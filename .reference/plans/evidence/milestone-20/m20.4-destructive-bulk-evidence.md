# M20.4 — Destructive & bulk actions: evidence

> Status: **verified** (2026-10-10). Slices **M20i** (session delete) and
> **M20j** (bulk memory decisions). Per-slice evidence; M20 is in progress.

## M20i — Session delete

- **Backend:** `DELETE /core/sessions/:id` removes the session, transcript,
  and session-scoped operational rows. `tool_requests` (the only RESTRICT FK)
  is cleared first; the `sessions` delete then cascades
  messages / approvals / clarifications / agent runs / todos (and their
  events + FTS rows) and SET NULLs `cron_jobs.session_id`.
- **Derived memory is deliberately kept.** `memory_candidates`, `claims`,
  `promotion_journal`, `claim_history`, `source_reliability`, and `persona_*`
  live in the **separate memory DB** (`MEMORIES_SCHEMA_SQL` → `memoryDbPath`)
  with no FK to `sessions`, so a session delete cannot touch them. The operator
  deletes memory separately — this makes it harder to erase usage patterns by
  wiping sessions, and means clearing old sessions does not remove wanted facts.
- **Client:** the Chat header gains a **Delete** button (open session only)
  with an inline confirm. `docs/usage.md` documents the deliberate friction
  (open-to-delete, no hover-delete) and the memory-persistence rule.

## M20j — Bulk memory decisions

- **Backend:** `POST /core/promotions/bulk { decision }` approves or rejects
  every open promotion's approval (resolving each approval's owning session
  server-side); approve runs a single sweep. Per-item failures are counted,
  never thrown.
- **Client:** the Memory/Review queue gains **Approve all** / **Reject all**
  with a confirm that states how many rows are affected.

## Unit

Core **1194 unit / 66 e2e**; client **198 tests**; `tsc`/`eslint` + `ng build`
clean. New test: `sqlite-session.repository.spec.ts` proves a session + its
tool request are removed while the (separate) memory DB is untouched.

## Live

```
DELETE /core/sessions/:id                    → 200 deleted
  session still listed? false
DELETE /core/sessions/does-not-exist         → 404
memory candidates before/after               → 5 / 5   (unchanged — memory persists)

POST /core/promotions/bulk {decision:"reject"} → 200 {applied:120, failed:0}
POST /core/promotions/bulk {decision:"nope"}   → 400
```

### ⚠️ Live-test side effect

The bulk probe used `reject`, which **rejected 120 pending promotions** in the
live instance (state → denied; they will not auto-promote). The underlying
memory candidates are intact, so nothing was lost from the ledger, but those
promotions will not become beliefs on their own. A gentler probe (`approve`,
or a fresh instance) would have been the better choice.
